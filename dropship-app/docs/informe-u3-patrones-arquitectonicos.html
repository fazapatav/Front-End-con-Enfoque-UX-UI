1. Introducción y Contexto de la Evolución

La Entrega 1 de este módulo estableció la propuesta conceptual y el prototipo inicial de DropShip Pro, una plataforma SPA de dropshipping white label construida con React 19 y Vite 8. La aplicación implementó nueve vistas funcionales organizadas en cuatro módulos (Panel del Vendedor, Pedidos y Envíos, Inventario y Bodega, Billetera Virtual), empleando React Router DOM para la navegación y CSS Custom Properties como sistema de diseño.

En esa primera entrega, el manejo del estado global se apoyó en Context API + useReducer, acercándose de manera empírica al patrón Flux. Sin embargo, las responsabilidades no estaban formalmente separadas: las Views construían objetos de acción directamente dentro del código del componente, y el reducer y el estado inicial coexistían en el mismo archivo de contexto.

La presente Entrega 2 representa la transición de una propuesta conceptual a una arquitectura formalmente estructurada. Se formaliza el patrón Flux mediante la separación explícita de cuatro capas independientes: Actions, Dispatcher, Store y Views. Este proceso de maduración arquitectónica permite analizar el impacto real del patrón en mantenibilidad, testabilidad y escalabilidad del sistema.

2. Selección y Justificación del Patrón Arquitectónico

2.1 Patrón Seleccionado: Flux

Para la evolución de DropShip Pro se seleccionó el patrón Flux, creado por Facebook (Meta) en 2014 específicamente para aplicaciones React de tipo SPA. Flux define un flujo de datos estrictamente unidireccional que atraviesa cuatro capas fijas:

    View  →  Action Creator  →  Dispatcher  →  Store  →  View
    ────     ──────────────     ──────────     ─────     ────
   (UI)      (acciones puras)   (enruta)     (estado)   (re-render)

2.4 Justificación por Impacto en Calidad Arquitectónica

Mantenibilidad

La separación de capas garantiza que una modificación en la lógica de negocio (ej: cambiar cómo se calcula el saldo de la billetera) afecta exclusivamente a reducer.js y actions.js, sin tocar ningún componente de UI. En MVC o MVP, este cambio podría propagarse al Controller o Presenter. Con Flux, la regla es clara: las Views nunca contienen lógica de negocio.

Testabilidad

El appReducer es una función pura (state, action) → newState. No tiene efectos secundarios, no accede al DOM, no hace llamadas HTTP. Esto permite testearlo exhaustivamente con Jest o Vitest sin necesidad de montar ningún componente:

// Prueba unitaria del reducer (sin React, sin DOM)
import { appReducer, initialState } from "../src/store/reducer";
import { updateWallet }             from "../src/store/actions";

test("UPDATE_WALLET incrementa el saldo", () => {
  const action = updateWallet({ balance: 2950000 });
  const newState = appReducer(initialState, action);
  expect(newState.wallet.balance).toBe(2950000);
  // initialState no fue mutado
  expect(initialState.wallet.balance).toBe(2450000);
});

Escalabilidad

Agregar un nuevo dominio (ej: notifications con lógica compleja) implica únicamente añadir una nueva constante a ACTION_TYPES, un nuevo Action Creator en actions.js y un nuevo case en reducer.js. Las Views existentes no se modifican. Esta propiedad de extensión sin modificación (principio Open/Closed) es inherente a Flux.

3. Definición de Responsabilidades por Capas

3.1 Capa Actions (src/store/actions.js)

Responsabilidad única: Definir el vocabulario de cambios posibles del sistema. Esta capa tiene dos elementos inseparables:

  • ACTION_TYPES: Objeto de constantes que identifica unívocamente cada tipo de acción. Previene errores de tipeo (una cadena mal escrita es indetectable en runtime; una constante inexistente es undefined y fácil de depurar).
  • Action Creators: Funciones puras que construyen y retornan objetos de acción. Las Views nunca construyen { type: '...', payload: ... } manualmente; siempre invocan un Action Creator.
// src/store/actions.js — Capa de Actions

export const ACTION_TYPES = {
  TOGGLE_THEME:          "TOGGLE_THEME",
  TOGGLE_SIDEBAR:        "TOGGLE_SIDEBAR",
  UPDATE_BRAND:          "UPDATE_BRAND",
  UPDATE_WALLET:         "UPDATE_WALLET",
  CLEAR_NOTIFICATIONS:   "CLEAR_NOTIFICATIONS",
};

// Action Creator: retorna { type, payload? } — sin side-effects
export function updateWallet(walletData) {
  return { type: ACTION_TYPES.UPDATE_WALLET, payload: walletData };
}

export function updateBrand(brandData) {
  return { type: ACTION_TYPES.UPDATE_BRAND, payload: brandData };
}

export function toggleTheme()         { return { type: ACTION_TYPES.TOGGLE_THEME }; }
export function toggleSidebar()       { return { type: ACTION_TYPES.TOGGLE_SIDEBAR }; }
export function clearNotifications()  { return { type: ACTION_TYPES.CLEAR_NOTIFICATIONS }; }

3.2 Capa Dispatcher (src/context/AppContext.jsx)

Responsabilidad única: Actuar como canal de comunicación entre las Views y el Store. En la implementación de React, el Dispatcher es la función dispatch provista por useReducer. AppContext.jsx monta el Store, obtiene el Dispatcher y los expone a toda la aplicación mediante el patrón Provider/Consumer:

// src/context/AppContext.jsx — Capa Dispatcher

import { createContext, useContext, useReducer } from "react";
import { appReducer, initialState } from "../store/reducer";

const AppContext = createContext(null);

export function AppProvider({ children }) {
  // useReducer conecta Dispatcher (dispatch) con Store (appReducer + initialState)
  const [state, dispatch] = useReducer(appReducer, initialState);
  return (
    <AppContext.Provider value={{ state, dispatch }}>
      {children}
    </AppContext.Provider>
  );
}

export function useApp() {
  const ctx = useContext(AppContext);
  if (!ctx) throw new Error("useApp must be used within AppProvider");
  return ctx;
}

3.3 Capa Store — Reducer (src/store/reducer.js)

Responsabilidad única: Mantener el estado de la aplicación y aplicar transformaciones inmutables ante cada acción. El reducer es una función pura que recibe el estado actual y una acción, y retorna un nuevo estado sin modificar el anterior:

// src/store/reducer.js — Capa Store

import { ACTION_TYPES } from "./actions";

export const initialState = { theme: "light", sidebarOpen: true,
  user: { name: "Carlos Mendoza", email: "carlos@dropshippro.com",
    brand: { name: "Mi Marca", address: "Calle 123 #45-67, Bogotá" } },
  wallet: { balance: 2450000, currency: "COP" }, notifications: 3 };

export function appReducer(state, action) {
  switch (action.type) {
    case ACTION_TYPES.TOGGLE_THEME:
      return { ...state, theme: state.theme === "light" ? "dark" : "light" };

    case ACTION_TYPES.UPDATE_WALLET:
      return { ...state, wallet: { ...state.wallet, ...action.payload } };

    case ACTION_TYPES.UPDATE_BRAND:
      return { ...state, user: { ...state.user,
          brand: { ...state.user.brand, ...action.payload } } };

    case ACTION_TYPES.TOGGLE_SIDEBAR:
      return { ...state, sidebarOpen: !state.sidebarOpen };

    case ACTION_TYPES.CLEAR_NOTIFICATIONS:
      return { ...state, notifications: 0 };

    default:
      return state; // Invariante: acción desconocida → sin cambios
  }
}

Garantía de inmutabilidad: Cada case emplea el operador spread (...) en todos los niveles del árbol de estado. React detecta el cambio de referencia del objeto y re-renderiza únicamente los componentes suscritos al valor modificado.

3.4 Capa Views (src/pages/**, src/components/**)

Responsabilidad única: Presentar información al usuario y traducir eventos de UI en acciones. Las Views solo conocen los Action Creators de la capa Actions; son agnósticas respecto al formato interno del estado o la lógica del reducer:

// src/pages/Wallet/Wallet.jsx — Capa View
// Importa Action Creator, no construye objetos de acción manualmente

import { updateWallet } from "../../store/actions";

export default function Wallet() {
  const { state, dispatch } = useApp();
  const [selectedAmount, setSelectedAmount] = useState(null);

  const handleRecharge = () => {
    if (!selectedAmount) return;
    // View invoca Action Creator → dispatch recibe objeto de acción correcto
    dispatch(updateWallet({ balance: state.wallet.balance + selectedAmount }));
    setSelectedAmount(null);
  };
  // ...
}

4. Modelo de Gestión de Estado

4.1 Estado Global vs Local — Criterio de Separación

DropShip Pro aplica el principio de mínima elevación del estado: un estado sube al Store global únicamente si dos o más componentes en diferentes rutas necesitan leerlo o modificarlo. De lo contrario, permanece local al componente con useState.

EstadoTipoJustificación
themeGlobal (Store)Afecta TODOS los componentes vía CSS custom properties
sidebarOpenGlobal (Store)Layout y Header lo leen/modifican desde posiciones distintas del DOM
wallet.balanceGlobal (Store)Header lo muestra, Wallet lo modifica, Shipping lo valida
user.brandGlobal (Store)Brand lo edita; Picking y Shipping lo leen para etiquetas white label
notificationsGlobal (Store)Header badge lo muestra; múltiples vistas potencialmente lo modifican
search (Catalog)Local (useState)Solo Catalog.jsx lo usa; correcto que se reinicie al navegar
step (Shipping)Local (useState)Solo Shipping.jsx lo usa; el wizard debe reiniciarse entre envíos
selectedAmount (Wallet)Local (useState)Selección temporal antes de confirmar; no debe persistir
completedIds (Picking)Local (useState)Efímero de sesión; en producción vendría del backend

4.2 Flujo de Datos Unidireccional

A diferencia de patrones como MVC con two-way binding, Flux garantiza que el estado siempre fluye en una sola dirección:

    STORE (fuente de verdad)
         │
         │ state (vía Context)
         ▼
      VIEWS (leen estado, renderizan UI)
         │
         │ evento de usuario → Action Creator → dispatch(acción)
         ▼
    DISPATCHER (recibe y enruta)
         │
         │ appReducer(state, action) → newState
         ▼
      STORE (actualizado, notifica a Views)
         │
         └── (ciclo se repite)

Este ciclo cerrado elimina la clase de bugs donde dos componentes modifican el mismo estado simultáneamente sin conocerse — problema frecuente en MVC cuando múltiples Controllers pueden mutar el mismo Model.

4.3 Action Creators como Interfaz de Acceso al Store

Los Action Creators actúan como la API pública del Store. Las Views nunca dependen del formato interno de las acciones; si en el futuro el tipo de acción cambia (ej: de UPDATE_WALLET a WALLET/RECHARGE), el cambio ocurre únicamente en actions.js — no en los componentes:

// ANTES (Entrega 1) — View conoce el formato interno:
dispatch({ type: "UPDATE_WALLET", payload: { balance: newBalance } })

// DESPUÉS (Entrega 2) — View usa la interfaz pública:
dispatch(updateWallet({ balance: newBalance }))

// Si cambia el formato de acción, solo se modifica actions.js.
// Las 9 Views que llamen updateWallet() no necesitan modificarse.
Principio de encapsulación: Las Views desconocen la estructura interna de las acciones. Están desacopladas del Store por la capa de Action Creators.

Action Creators en uso — Layout.jsx

El componente Layout utiliza tres Action Creators para las tres acciones globales que dispara:

// Importación de Action Creators (no de strings ni objetos literales)
import { toggleSidebar, toggleTheme, clearNotifications } from "../../store/actions";

// En el JSX:
<button onClick={() => dispatch(toggleSidebar())}>☰</button>
<button onClick={() => dispatch(clearNotifications())}>🔔{state.notifications}</button>
<button onClick={() => dispatch(toggleTheme())}>
  {isDark ? <Sun /> : <Moon />}

Inmutabilidad del State — Verificación

Cada case del reducer retorna un nuevo objeto en TODOS los niveles del árbol de estado, garantizando que React detecte los cambios por comparación de referencia (Object.is):

case ACTION_TYPES.UPDATE_BRAND:
  return {
    ...state,                    // nivel 1: nuevo objeto raíz
    user: {
      ...state.user,             // nivel 2: nuevo objeto user
      brand: {
        ...state.user.brand,     // nivel 3: nuevo objeto brand
        ...action.payload        // merge con datos nuevos
      }
    }
  };
  // Resultado: React detecta state !== prevState → re-render de consumidores

Testabilidad del Reducer

Al ser el reducer una función pura exportada de forma independiente, puede testearse sin montar ningún componente React:

import { appReducer, initialState } from "../src/store/reducer";
import { toggleTheme, updateWallet } from "../src/store/actions";

describe("appReducer", () => {
  test("TOGGLE_THEME alterna entre light y dark", () => {
    const s1 = appReducer(initialState, toggleTheme());
    expect(s1.theme).toBe("dark");
    const s2 = appReducer(s1, toggleTheme());
    expect(s2.theme).toBe("light");
  });

  test("UPDATE_WALLET no muta el estado anterior", () => {
    const s1 = appReducer(initialState, updateWallet({ balance: 0 }));
    expect(s1.wallet.balance).toBe(0);
    expect(initialState.wallet.balance).toBe(2450000); // sin mutación
  });
});

6. Análisis de Ventajas, Riesgos y Costos Arquitectónicos

6.1 Ventajas del Patrón Flux

VentajaDescripción técnicaImpacto en DropShip Pro
Flujo unidireccional Estado solo fluye en una dirección: Store → View → Action → Dispatcher → Reducer → Store Los bugs de estado (ej: saldo incorrecto en billetera) tienen un único punto de origen posible: el reducer. El tiempo de depuración se reduce significativamente
Inmutabilidad garantizada El reducer siempre retorna nuevos objetos mediante spread operator; nunca modifica el estado directamente En módulos financieros (wallet, transacciones) la imposibilidad de mutación accidental es una garantía de corrección operativa
Testabilidad del reducer appReducer es función pura: misma entrada → misma salida, sin side-effects Permite test coverage del 100% de la lógica de negocio del estado sin necesidad de React Testing Library ni JSDOM
Separación de capas Actions, Dispatcher, Store y Views tienen responsabilidades no solapadas y bien definidas Un desarrollador nuevo puede modificar la lógica de marca blanca tocando solo reducer.js y actions.js, sin riesgo de romper las Views
Alineación con React React fue diseñado originalmente para trabajar con Flux; Context + useReducer es la implementación nativa Cero overhead de librerías externas; el patrón se implementa con solo 2 archivos nuevos y refactoring de AppContext

6.2 Riesgos del Patrón Flux

RiesgoDescripciónMitigación aplicada

En el crecimiento se puede migrar a Zustand (selectores granulares) sin reescritura del reducer
Store único puede crecer Si el estado global escala a 20+ propiedades, reducer.js se vuelve difícil de mantener como un solo archivo Flux soporta múltiples Stores. En el roadmap: partir reducer.js en walletReducer.js, userReducer.js y combinarlos con combineReducers
Verbose para estado simple Agregar una nueva propiedad global requiere modificar 3 archivos (actions, reducer, y los consumers) Es el costo del desacoplamiento. Para estado estrictamente local se usa useState, evitando el overhead del Store
Curva de aprendizaje inicial Los desarrolladores nuevos deben comprender el ciclo Flux antes de poder contribuir Los comentarios en actions.js y reducer.js documentan el flujo explícitamente; la convención de nombres es autodescriptiva

6.4 Decisión Estratégica — Análisis ROI Arquitectónico

Para un MVP de 9 vistas con 5 propiedades de estado global, el costo de implementar Flux formalmente es mínimo (2 archivos, refactoring no destructivo), mientras que los beneficios son estratégicamente significativos:

  • El 100% de la lógica de negocio del estado es testeable sin UI.
  • La capa de Actions encapsula el vocabulario de cambios; cualquier reestructuración futura del estado no propaga cambios a las Views.
  • La inmutabilidad es un requerimiento no funcional crítico en módulos financieros (billetera, transacciones); Flux la garantiza por diseño.
  • La evolución a Redux Toolkit o Zustand en el roadmap de enterprise es trivial: el reducer y las action creators son compatibles con ambas librerías.
⚠️ Riesgo residual identificado

El Context re-render global es un riesgo de performance cuando el estado escala. Este riesgo no aplica en el MVP actual (9 vistas, estado de 5 propiedades), pero debe contemplarse en el roadmap: migrar a Zustand con selectores permite resolver este riesgo sin reescribir el reducer.

7. Conclusiones

La Entrega 2 materializó la transición de una implementación empírica del manejo de estado a una arquitectura Flux formalmente estructurada. Los resultados concretos del proceso son:

  • El patrón Flux fue implementado mediante la separación explícita de cuatro capas independientes: actions.js (Action Types + Creators), AppContext.jsx (Dispatcher), reducer.js (Store) y los componentes de página (Views).
  • El prototipo funcional se verificó exitosamente con npx vite build, produciendo un bundle de 278 KB sin errores.
  • Las Views ahora invocan Action Creators en lugar de construir objetos de acción manualmente, eliminando el acoplamiento al formato interno del Store.
  • El appReducer es una función pura exportable e independientemente testeable, lo que eleva la testabilidad del sistema del nivel de integración al nivel unitario.

Desde una perspectiva estratégica, Flux demostró ser el patrón de mayor retorno arquitectónico para una SPA React de dominio financiero: su flujo unidireccional previene la clase de bugs más costosa en sistemas de pagos (mutación de estado no rastreable), mientras que su alineación nativa con React minimiza el costo de implementación y elimina dependencias externas.

La arquitectura resultante cumple el principio de extensión sin modificación: cada nueva funcionalidad que requiera estado global puede integrarse añadiendo una constante a ACTION_TYPES, un Action Creator y un case al reducer, sin tocar ninguno de los nueve componentes de página existentes.
