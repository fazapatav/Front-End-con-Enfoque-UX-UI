1. Introducción: Evolución desde las Entregas Previas

Las entregas anteriores de este módulo establecieron una base arquitectónica sólida para DropShip Pro: la Entrega 1 definió el diseño UX/UI y la justificación del framework React; la Entrega 2 formalizó el patrón Flux con capas explícitas de Actions, Dispatcher y Store. Ambas entregas construyeron un monolito SPA funcional, coherente y bien estructurado.

La Entrega 3 representa una ruptura conceptual: la evolución del monolito hacia una arquitectura de microfrontends. Esta transición no implica reescribir el código existente, sino reorganizar sus responsabilidades en dominios independientes, con capacidad de despliegue autónomo y equipos propietarios claramente definidos.

El ejercicio evidencia que la arquitectura de software no es un estado estático, sino un proceso de toma de decisiones continuo, donde cada evolución responde a presiones organizacionales, técnicas y de negocio concretas.

2. Justificación Estratégica de Microfrontends

2.1 Crecimiento Organizacional Hipotético

Asumamos que DropShip Pro alcanzó tracción en el mercado latinoamericano y debe escalar. La organización evoluciona de un equipo de 3 personas a cuatro squads especializados:

SquadDominio de negocioEquipoCadencia de despliegue
Squad VendedorCatálogo, marca blanca, métricas3 devs + 1 UX2 veces/semana
Squad PedidosCreación y seguimiento de envíos4 devs + 1 QADiario
Squad BodegaInventario, picking, fulfillment2 devs + 1 ops1 vez/semana
Squad FinanzasBilletera, transacciones, conciliación3 devs + 1 auditorMensual (regulado)

Con cuatro squads de cadencias distintas, un monolito SPA se convierte en un cuello de botella organizacional: el Squad Pedidos no puede desplegar su módulo de envíos sin esperar que el Squad Finanzas apruebe sus cambios mensuales, y viceversa.

2.3 Por qué Microfrontends — Visión Arquitectónica

Los microfrontends no son una solución técnica, son una respuesta organizacional. Permiten que la estructura del software refleje la estructura del equipo (Ley de Conway inversa). Cada squad es propietario de su MFE: decide su tecnología, su ritmo de despliegue y su estrategia de testing, dentro del contrato de integración definido por el Shell.

Principio rector: "La arquitectura de un sistema debe reflejar la estructura organizacional del equipo que lo construye y mantiene." — Conway, 1967 (aplicación inversa: diseñar la arquitectura para habilitar la estructura de equipo deseada).

3. Definición de Dominios Funcionales

3.1 Criterios de Delimitación

Los dominios se definieron aplicando los principios de Domain-Driven Design (DDD): cada dominio debe tener un lenguaje ubicuo propio, datos que controla exclusivamente, y capacidades que no dependen de otros dominios para funcionar:

  • Alta cohesión interna: Las páginas de un mismo dominio comparten datos y flujos de negocio naturales.
  • Bajo acoplamiento externo: La comunicación entre dominios ocurre solo a través del Event Bus; nunca mediante imports directos entre MFEs.
  • Autonomía de despliegue: Un dominio puede cambiar sin que otros se vean afectados, siempre que respete el contrato de eventos.
  • Propietario único: Un solo squad es responsable de cada dominio.

3.2 Los Cuatro Dominios de DropShip Pro

VendorMFE Gestión de Oferta del Vendedor Dashboard, Catálogo, Mi Lista, Mi Marca 5174 Squad Vendedor
OrdersMFE Gestión del Ciclo de Vida de Pedidos Mis Pedidos, Nuevo Envío 5175 Squad Pedidos

3.3 Shell Orquestador

El Shell (App.jsx + Layout.jsx) no es un MFE: es la aplicación contenedora que gestiona:

  • Routing global y navegación (sidebar, header)
  • Estado compartido mínimo a través de AppContext (tema, saldo visible, marca)
  • Carga dinámica de cada MFE según la ruta activa
  • Fallbacks visuales (MFELoader) mientras el bundle del MFE se descarga

4.2 Estrategia Seleccionada: Composición Client-Side

Se seleccionó la composición en el cliente como estrategia de integración porque permite que cada MFE sea descargado de forma independiente en el navegador solo cuando el usuario lo necesita. Esto significa que cuando un usuario navega a la sección de Billetera, el navegador descarga únicamente el código de WalletMFE en ese momento; mientras tanto, los bundles de OrdersMFE, VendorMFE y WarehouseMFE permanecen dormidos en el servidor, listos para ser utilizados si el usuario navega hacia ellos. Esta aproximación client-side evita la necesidad de infraestructura adicional de servidor SSR (Server-Side Rendering), aprovechando que la aplicación ya es una SPA React madura.

La independencia de despliegue es el beneficio más directo de esta estrategia. Cada squad puede desarrollar su MFE en su propio repositorio, testear de forma aislada, y desplegarlo en su propio servidor o CDN sin necesidad de coordinar con otros equipos. El Shell actúa como un "orquestador neutral" que sabe dónde encontrar cada MFE en tiempo de ejecución y se encarga de cargarlo cuando sea necesario. Esta separación física de los artefactos (cada MFE es un bundle JavaScript independiente) refleja directamente la separación lógica de responsabilidades entre dominios de negocio.

El contrato de integración entre MFEs es deliberadamente minimalista: consiste únicamente en el Event Bus (un mecanismo de eventos publish/subscribe implementado en JavaScript nativo) y el estado compartido del Shell (datos como el tema visual, el saldo visible de la billetera, y la marca del vendedor). Esta claridad contractual elimina la ambigüedad operacional: cualquier comunicación entre dominios debe ocurrir a través de estos dos canales documentados y versionados. No hay importes directos entre MFEs, no hay dependencias ocultas, no hay sorpresas en el momento del despliegue.

4.3 Event Bus como Contrato Cross-MFE

El Event Bus (src/utils/eventBus.js) es el único mecanismo de comunicación entre dominios. Implementa el patrón Publish/Subscribe sobre la API nativa del navegador (window.CustomEvent):

// src/utils/eventBus.js — Contrato de eventos entre MFEs

export const EVENTS = {
  WALLET_BALANCE_UPDATED: "mfe:wallet:balance-updated",   // Wallet → Shell
  CATALOG_PRODUCT_ADDED:  "mfe:catalog:product-added",    // Vendor → Orders
  ORDER_CREATED:          "mfe:order:created",             // Orders → Warehouse
  BRAND_UPDATED:          "mfe:brand:updated",             // Vendor → Shell
};

export const eventBus = {
  emit(event, data) {
    window.dispatchEvent(new CustomEvent(event, { detail: data }));
  },
  on(event, handler) {
    window.addEventListener(event, handler);
    return () => window.removeEventListener(event, handler); // cleanup
  },
};

Flujo de comunicación implementado (WalletMFE → Shell):

// WalletMFE (src/pages/Wallet/Wallet.jsx) — EMISOR
const handleRecharge = () => {
  const newBalance = state.wallet.balance + selectedAmount;
  dispatch(updateWallet({ balance: newBalance }));
  // MFE Finanzas notifica al Shell del nuevo saldo
  eventBus.emit(EVENTS.WALLET_BALANCE_UPDATED, { balance: newBalance });
};

// Shell (src/components/Layout/Layout.jsx) — RECEPTOR
useEffect(() => {
  const unsub = eventBus.on(EVENTS.WALLET_BALANCE_UPDATED, () => {
    setWalletPulse(true);             // pulsa el chip de saldo en el header
    setTimeout(() => setWalletPulse(false), 1500);
  });
  return unsub;                        // cleanup al desmontar
}, []);

Se definieron dos zonas de estado con reglas estrictas de acceso:

ZonaMecanismoQuién puede leerQuién puede escribir

⚠️ Regla de gobernanza crítica

Ningún MFE puede importar directamente código de otro MFE. Ejemplo prohibido: import Wallet from '../wallet/Wallet.jsx' desde OrdersMFE. La única comunicación permitida entre dominios es a través del Event Bus o el estado compartido del Shell.

6. Reflexión Crítica y Decisiones Tomadas

6.1 Decisiones Arquitectónicas y su Justificación

Decisión 1: Simulación de Module Federation con React.lazy()

Se optó por React.lazy() en lugar de configurar @originjs/vite-plugin-federation con múltiples servidores. La razón es pragmática: un prototipo académico demostrable debe funcionar con un único npm run dev. Sin embargo, el código está estructurado de forma que la migración a Module Federation real requiere únicamente cambiar las líneas de import, sin tocar la lógica de ningún MFE:

// Ahora (simulado):
const WalletMFE = lazy(() => import("./mfe/wallet/WalletMFE"));

// En producción (Module Federation):
const WalletMFE = lazy(() => import("wallet/WalletMFE"));

Esta decisión refleja un principio fundamental: la arquitectura debe ser demostrable en cada etapa, incluso con aproximaciones de bajo costo técnico.

Decisión 2: Event Bus sobre window.CustomEvent

Se eligió window.CustomEvent en lugar de librerías como mitt o EventEmitter3. El razonamiento es de gobernanza: el Event Bus es el contrato más crítico de la arquitectura de microfrontends. Un mecanismo nativo del navegador garantiza que funciona independientemente del framework que use cada MFE en el futuro (Vue, Angular, Svelte), sin crear una dependencia compartida que podría generar conflictos de versiones.

Decisión 3: Mantener AppContext como estado compartido del Shell

Se decidió conservar el Context de React (Entrega 2) como mecanismo de estado compartido, en lugar de migrar a un sistema de estado externo al Shell. La justificación es que el estado compartido mínimo (tema, saldo visible, nombre de marca) es legítimamente responsabilidad del Shell — es UI compartida, no lógica de dominio. Cada MFE mantiene su estado de dominio de forma local y autónoma.

6.3 Aprendizajes Alcanzados

  1. La arquitectura de software es un problema organizacional antes que técnico. La decisión de adoptar microfrontends no se justifica por razones puramente técnicas, sino porque la estructura de equipos de la organización lo requiere. Este es el aprendizaje más significativo de la Unidad 4.
  2. El contrato entre componentes es más importante que la implementación interna. El Event Bus y el estado compartido del Shell son los contratos de la arquitectura. La implementación interna de cada MFE puede cambiar libremente, siempre que respete esos contratos.
  3. La evolución arquitectónica debe ser incremental. Las tres entregas demostraron que una arquitectura madura no se construye de una vez: primero la UI (Entrega 1), luego los patrones de estado (Entrega 2), luego la descomposición en dominios (Entrega 3). Cada paso fue aditivo y no destructivo.
  4. La testabilidad mejora con los límites de dominio. Cada MFE puede testearse de forma completamente aislada — sus páginas no tienen dependencias de otros MFEs. El Event Bus puede mockearse trivialmente en los tests: jest.spyOn(eventBus, 'emit').
Conclusión estratégica: DropShip Pro ha evolucionado de un prototipo de interfaz (Entrega 1) a una arquitectura formalmente estructurada con patrones (Entrega 2) y finalmente a un modelo orientado a dominios de negocio independientes (Entrega 3). Esta trayectoria refleja el proceso real de maduración de una plataforma de software: las decisiones arquitectónicas se toman en respuesta a presiones reales, no de forma especulativa.
